## 2. 缺陷与层判定

**层：规则层（R03a / R04a 实现）；handler `act_trigger_hypo` 不查读数也是成因，但拒绝应由确认规则给出**

- 现象两类：① 读数编号在 seed 里不存在（r-P0023-00480 夜间掉数、r-P0031-06666、r-P0012-09876、r-P0023-09999），handler 读不到读数、值为空、置信 0.3，照样写 AlertEvent；② 读数存在但值根本不是低血糖（r-P0031-00530=10.8、r-P0012-00330=11.7、r-P0023-00620=12.1），按实际值写一条「低」级 AlertEvent。全部 committed。
- 定位：`r03a` 开头 `if g is None or g >= 3.0: return ok`，`r04a` 开头 `if g is None or not (3.0 <= g < 3.9): return ok`——读数为空或不在本级区间时直接放行，没有「请求的处置与读数对不上」这一判。
- r47 是 W52 遗留（路由置信度 2026-10-25 修正为 0.95 后可评到 R04a），与 W53 的 0735 / 0751 / 0764 同型，说明此前的修复（若有）没覆盖这条路径。
- r54 的 rule_id 是 `hypo_immediate_action`（未写级别），业务期望 R03a（口语说 2.9）。

## 3. 根因修

**P33a（proposal 57）**：R03a / R04a 是实时低血糖告警的**确认条件**（IR：「连续 2 个读数确认 G<3.0 / 3.0≤G<3.9 即触发」），引用一条读数发起处置时，这条读数就是确认的起点。补两条前提：① 引用的读数必须存在；② 读数值必须处于低血糖区间（<3.9）。不满足即「本级确认不成立」，由请求级别对应的规则拒：rule_id 解析出 Level 2 / R03 → R03a，Level 1 / R04 → R04a，未写级别 → 两条都判（r54 由此得到 R03a）。
边界：读数 <3.9 但级别与请求不一致（请求 L1、实际 2.6）不在此拦——handler 按读数值定告警级别，原有连续确认分支照常评，避免把真低血糖挡在门外；只在带 reading_id 的调用上生效，`推送告警` 不受影响。新增 `_requested_hypo_level` / `_hypo_trigger_unconfirmed` 两个小函数，R03a 与 R04a 各自调用、各自给级别，不共用判定函数体（守 IR §4.4 的四函数分离约束）。
