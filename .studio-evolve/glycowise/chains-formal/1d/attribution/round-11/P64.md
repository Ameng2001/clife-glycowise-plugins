# P64 · D12 签发对象不存在仍放行

- 链：1d（本链当前状态 = h_s + P24a + P25a + P29a + P31a + P32a + P34a–P40a）
- 窗口：2026-W54
- 来源案例（Dᵢ，`P64-Di.yaml`）：出口签发闸-r57（t-0858）、-r58（t-0867）、-r59（t-0875）
- 缺陷层：规则层（`_fde.d12`）
- 提案：P64a（根因修，proposal 121）；没有可用的朴素修

## 1. 复现

| 案例 | 路由参数 | 实情 | 期望 | 本链实际 |
|---|---|---|---|---|
| r57 | draft_id=d-P0088-01，signer=黄医生 | 草稿不存在 | rejected(D12) | 签发方案·commit（进 HIL） |
| r58 | draft_id=plan-P0066-w41 | 这是已签发方案（PlanSigned），不是草稿 | rejected(D12) | commit |
| r59 | draft_id=d-P0007-02 | 草稿不存在 | rejected(D12) | commit |

handler `act_sign` 遇到这种情况照样会写一条 PlanSigned，content_snapshot 和 patient_id 都是空的。

## 2. 根因

D12 的做法是按「草稿内容的类别 × 签发人资质」分流签发人，这有一个前提：签的对象是一份**真实存在的待签草稿**。草稿号查不到时，类别推断落到兜底的「综合」；签发人是医师时 scope 为 None，直接放行，结果签发了一份不存在的方案。业务侧的口径是「签发对象不存在就该拒」，和 P47a 对 C20 的处理一样（指名的对象不存在就拒）。

## 3. 根因修 P64a（proposal 121）

在 d12 开头加一道检查：`draft_id` 有值但 PlanDraft 里查不到，就拒。拒绝说明分两种：如果这个编号在 PlanSigned 里查得到，说明「已签发方案，不是待签草稿（系统没有复签动作）」；否则说明「在系统里不存在」。修改建议是「核对草稿号；需要改方案请先生成新草稿再签发」。

规则名沿用 D12。业务侧在 note 里写的是「也可以另立存在性检查，规则名待本体负责人定」，这里先挂在 D12 上，因为 D12 是签发方案上唯一读草稿的守卫。如果本体负责人决定另立规则，只需改名，判定逻辑不用动。

补丁 `P64a.patch` 共 17 行，只改 `_fde.py`。

## 4. 朴素修：五条机械规则逐条判定

| 规则 | 是否适用 | 理由 |
|---|---|---|
| ① 放宽阈值 | 不适用 | D12 没有数值阈值 |
| ② 跳过缺参数的校验 | 不适用 | Dᵢ 要拒；草稿不存在本身就是「缺参数」，跳过校验恰好就是现在放行的行为 |
| ③ 删掉命中的规则分支 | 不适用 | Dᵢ 上命中的是 `scope is None → ok`（签发人是医师）。机械地删掉这一支，医师的 scope 就是 None，`cat not in None` 会抛 TypeError。沙箱实测：Dᵢ 三条在前序签发步骤就报 SETUP_FAILED:6:签发方案:TypeError，pass=null，不是拒，Dᵢ 不过。删类别兜底「综合」那一支也一样，医师照样放行 |
| ④ hard 改 soft | 不适用 | D12 已经是 hard |
| ⑤ 把 Dᵢ 命中的字面量加进匹配 | 不适用 | D12 匹配的是草稿正文（药名 / TIER_RE / 运动 / 饮食），Dᵢ 的草稿不存在，正文为空，没有可加的字面量。把 draft_id 写成黑名单不算「加进现有匹配」 |

所以 P64 没有朴素修。
