## 2 定位

- `r03a` 开头 `if g is None or g >= 3.0: return ok`，`r04a` 开头 `if g is None or not (3.0 <= g < 3.9): return ok`：读数不存在（g=None）或值不在本级区间都直接放行。
- `act_trigger_hypo` 不管读数是否存在、值是多少，都按值分级（None / ≥3.9 → 「低」）写一条 AlertEvent。
- 两条 post_write 规则都放行，告警就落了库。

IR：R03a / R04a 是实时告警的**确认条件**（连续 2 个读数确认 G<3.0 / 3.0≤G<3.9），`触发低血糖处置` 的语义是「基于一条读数」发起处置。读数缺失或根本不低时，确认无从谈起。对照同组：W44 0118 等「有读数但前一读数不连续」的条目早已被 P6 拒，说明「无法确认就拒」是既定口径；只是「读数本身不存在 / 不低」这两种情况被开头的放行分支吞掉了。

## 3 根因修 P45a（proposal 85）

带 `reading_id` 的低血糖处置请求，确认的起点就是这条读数：

- 读数不存在 / 没有值 → 无法确认，拒；
- 读数值 ≥3.9 → 与低血糖处置请求对不上，拒；
- 由哪条规则拒看 rule_id：写明 Level 2（level_2 / L2 / R03a / 二级）归 R03a，写明 Level 1 归 R04a，没写级别（如 hypo_immediate_action）两条都拒；
- rule_id 指向预测告警（R05 / 预测 / predict）或高血糖（R11 / hyper）的不是低血糖确认路径，不在此列；
- 不带 reading_id 的调用（推送告警也挂了这两条规则）照旧。

原有的连续读数判定原样保留在后面。handler 不改：两条 post_write 规则拒了，暂存的告警会随之回滚。

补丁 `P45a.patch`：`_fde.py` +37 / −0（新增 `_hypo_request_unconfirmable` 与三条 rule_id 识别正则，r03a / r04a 各加 3 行入口）。

不处理的情况：读数在低血糖区间、但与请求级别不符（例如 3.5 的读数按 Level 2 发起）。Dᵢ 不涉及，IR 也没写这一判，留作登记。
