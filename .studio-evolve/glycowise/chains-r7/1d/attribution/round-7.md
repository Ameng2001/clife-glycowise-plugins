## 2. 缺陷定位

**D⁻₁ · R44 只看措辞**（4 条）。R44 判「是否闭环请求」只看 `action_taken` 自由文本里有没有「闭环 / 结案 / 关闭…」。路由时大模型把用户的「可以闭环了」「闭掉」改写成「确认脱离低血糖风险」「已回升至安全范围」「补糖复测」「已进食」，关键词丢了。同组判对的 r30 / r33 恰好把「结案」写进了处置说明。

更深一层是**中间表示缺口**：`响应并回执告警` 只写 AlertAck，告警没有「已闭环」状态，闭环意图在本体里没有结构化表达，只能从文字猜。根治要给动作加闭环参数或给 AlertEvent 加闭环状态，但这会改变路由意图的形状，manual 回放测不出来（录制的 route 里没有这个参数），需要 live 路由臂——与 P15 同类，登记为中间表示缺口，本轮不立案。

**D⁻₂ · R51 只认写法清单**（1 条）。TIER_RE 认 L1、分层结论、「分层是一级 / 分层为二级」等写法；「这期评下来是 2 级」没有「分层」二字，漏过。P0012 的种子 tier_label = L2，消息里的「2 级」正是她的内部分层。

## 5. 流程发现（报导师）

- **同一缺陷的根因与朴素在链上先后判**（本轮实测）：根因在前时，朴素修要么补丁冲突（P20b），要么判的是已修好的状态（P21b，Dᵢ 起点 1.0 → 必然「无严格改善」）。两种都不是对朴素修本身的检验。这不影响 P-A（八臂都对 hᵢ 分别判两份），只影响 P-B 两条链各自的接受序列。**应在 v5 一并预登记**，候选：(i) 链上只走根因修，朴素修只进 P-A；(ii) 链上同一缺陷的两份都对**同一个链状态**判，接受其中 ΔA 较大者（平手取根因），另一份记「同缺陷已解」。建议 (i)：RQ-2 比的是两种闸门下本体的成长，朴素修是 RQ-1 的分歧来源，放进链里只会制造冲突记录。
- **R44 / 闭环的中间表示缺口**：登记为路由层 / 中间表示候选，与 P15 同类，需 live 路由臂才能测。
