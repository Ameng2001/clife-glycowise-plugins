# clife-glycowise-plugins

控糖场景的完整设计资料：从实地调研到产品设计、需求文档、界面线框，再到可编译的本体插件骨架。

场景是社区医养门店的血糖管理服务。**现状是业务动作在做，但没有系统承载**：分诊、问诊建档、体测、方案、群跟进这五段全靠人工——健康管理侧是纸质方案本加飞书多维表格加企微群拼起来的，体测设备当场打印纸质报告、数据不进任何系统；居家段更彻底，患者在群里口头汇报指血，健管师手抄进表格，人一外出就不测不报。

所以这个项目不是「给已有流程补一段 CGM 数据」，而是**把整条链做成系统**：门店侧五段 + 居家段 CGM。CGM 是这条链的最后一段，不是全部。顺序上门店侧在前——没有患者档案与体测基线，CGM 数据接进来无处可挂。

## 三条贯穿全局的约束

1. **CGM 是第三类医疗器械**。平台与门店都不持经营许可，器械交易走持证方，门店纯引流不碰货不收款。
2. **服务与产品物理分离**。合作方在售的医学营养产品是固体饮料（普通食品），不得宣称降糖或逆转，服务包合同、收款、话术、AI 输出里都不能出现产品。
3. **AI 不得自动生成处方**（互联网诊疗监管细则第 21 条）。智能体只能做数据解读、指南级生活方式建议、监测提醒与异常转介；分型分级结论、用药、疗程方案必须由医师或注册营养师签发后才能推送。

## 分期只有一条边界

**一期无实时告警。** 通道形态（云云对接或 SDK）是实现选择，不是分期条件。

一期保留全部回顾性能力：数据自动入平台、指标计算、数据充分性门槛可达标、餐后响应配对、方案草稿与医师签发、结营解读、缓解判定。**损失的只有时延，不是数据**——传感器本地缓存，周期性同步一次即可回填完整历史。

二期才做采集盒、自建 App、蓝牙直连、实时告警与夜间值班。这四件事全挂在实时告警下面，砍掉后一期范围立刻收敛。

## 当前进展与待决

设计阶段完成，本体已编译成插件骨架（172 处 `TODO(FDE)` 待填，数量大是本体建模的预期结果——把「哪些必须人填」显式化）。

**卡着的两个问题都在厂商侧**，详见台账 D 类：

- 硅基是否**书面允许第三方专用设备承载其 SDK**。若否，二期采集盒方案整体作废。这是授权条款问题不是技术问题。
- **传感器芯片侧缓存深度**。它决定患者最长可以多久不同步一次，进而决定数据充分性能否达标、缓解判定能否成立。走云云对接**并不能规避**这个依赖。

另有一条待临床核实：餐后高响应判据里的 `R2h ≥1.7` 是把峰值增幅的分界值挪用到 2h 回落值上，无独立依据，上线前必须确认。
