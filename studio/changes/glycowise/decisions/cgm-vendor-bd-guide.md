# CGM 厂商对接 · 商务谈判要点指南

> 版本 1.0 · 2026-09-04 · 适用于硅基动感（已确认接入）、三诺（拟谈第二供应商）及后续厂商
>
> **给谁看**：负责与 CGM 厂商谈合作的商务同事。
> **怎么用**：第 1 节先看，它解释了为什么这些问题必须在**签约前**问清楚。第 2 节是必问清单，建议直接打印带去会谈，逐项打勾。第 5 节是本项目已经踩过的坑。

---

## 1. 为什么这份指南存在

本项目在两周内，因为"问了才知道"改了三次设计：

| 我们以为 | 实际 | 代价 |
|---|---|---|
| 国内厂商都没有可用接入通道，只能靠患者上传截图 | 硅基可以接入 | 整个一期方案推翻重做 |
| 拿到"SDK"就解决了 | 是**移动端** SDK，装不进成品蓝牙网关 | 引出采集盒与自建 App 的产品形态级决策 |
| 允许多个蓝牙连接是好事 | 允许，但**显著缩短传感器续航** | 连接策略重新设计，且冲击服务包成本模型 |

**规律**：厂商销售说的"支持数据对接"，和工程师需要的"可编程接口 + 原始数据 + 明确的时间语义"，是两件事。这些差异在签约前问一句就能澄清，签约后发现则可能推翻整个产品方案。

**因此本指南的第一原则：技术人员必须参加商务会谈**，或至少在会前把第 2 节清单交给对方技术接口人书面回答。

## 2. 必问清单（打印带走，逐项打勾）

### A 组 · 数据可得性 —— 先问这组，它决定合作还值不值得谈

> **A1 是全场最重要的一个问题。** 如果答案是"只给汇总报告"，那么我们的指标层、临床规则库、餐后分析、服务分层全部落空，合作价值大幅降低，后面的问题可以不用问了。

| # | 问什么 | 为什么重要 | 好的答案 | 危险信号 |
|---|---|---|---|---|
| **A1** | **给原始读数，还是只给汇总指标和 AGP 报告？** | 决定我们能否自建指标层。只有原始读数才能算 TIR/TBR/CV/GMI、做餐后响应分析、做服务分层 | 给原始读数（逐点） | "我们提供标准 AGP 报告"——这是**报告不是数据** |
| A2 | 采样间隔是多少？ | 决定数据密度与后续告警时延。5 分钟 vs 15 分钟差三倍 | 明确的数字 | 含糊其辞、"看情况" |
| A3 | 历史数据能回溯多久？一次能拉多长区间？ | 决定补数能力与首次接入时的历史迁移 | 明确天数与单次窗口上限 | 只能拉当前传感器周期 |
| A4 | **每条读数带不带传感器侧序号？** | 决定我们的去重键能否不依赖时间戳。**这条一旦缺失会导致后期历史数据无法重算，缓解判定的前后对比失效** | 默认带 | 只有时间戳 |
| **A5** | **时间戳是"传感器测量时刻"还是"载体/服务器接收时刻"？** | 如果是接收时刻，所有基于时间的分析（夜间统计、餐后配对）全部失真，且无法通过调参补救 | 测量时刻 | "上传时间"、答不上来 |
| **A6** | **传感器本地能缓存多少读数？断连几天后重连能补回来吗？** | 决定患者最长可以多久不同步一次。直接决定我们的数据完整性能不能达标 | 明确的小时/天数，且支持断点回补 | "建议保持连接"——回避了问题 |
| A7 | 数据字段完整清单？ | 趋势箭头、变化率、质量标记、校准状态、预热标记、传感器序列号，每一个都有用途 | 给出字段文档 | 只给"时间+数值" |
| A8 | 传感器标称佩戴天数，以及实际中位数？ | 服务包按枚配量，标称与实际的差直接吃掉毛利 | 两个数字都给 | 只给标称值 |

### B 组 · 接入形态

| # | 问什么 | 为什么重要 |
|---|---|---|
| **B1** | **有云到云接口吗？还是只有 SDK？** | 有云到云 = 我们不用做 App，省一大笔开发。只有 SDK = 必须自建 App 承载 |
| B2 | SDK 是移动端、嵌入式，还是给裸协议文档？ | **移动端 SDK 装不进成品网关**。这一条决定了硬件形态 |
| B3 | SDK 支持哪些平台？iOS 后台限制怎么处理？ | iOS 后台蓝牙不可靠，影响采集策略 |
| B4 | 允许几个蓝牙连接并存？**并存对传感器续航有多大影响（要具体数字）** | 允许 ≠ 免费。要问"14 天会变成几天"，不要接受"有一些影响"这种回答 |
| B5 | 云到云的话：延迟多少？轮询还是 webhook？配额与限流？支持游标断点续传吗？ | 决定我们的拉取调度与背压设计 |
| B6 | 有沙箱/测试环境吗？文档在哪？技术支持怎么响应？ | 没有沙箱意味着只能拿真实患者数据调试，这是合规问题 |
| B7 | SDK/固件升级会不会破坏我方集成？有向后兼容承诺吗？提前多久通知？ | 厂商一次静默升级可以让我们线上全挂 |

### C 组 · 合同必须写死的条款

> 这组是本指南里最容易被忽略、但代价最高的部分。技术能力谈得再好，不写进合同都可能变。

| # | 条款 | 说明 |
|---|---|---|
| **C1** | **原始点数据的可得性写进合同** | 这是核心条款。不能停留在"技术上支持"，要写成厂商的交付义务。否则技术对接时被降级为"只给报告"，我们没有救济手段 |
| **C2** | **授权撤回机制** | 厂商能否单方面停掉我方数据访问？要约定提前通知期（建议 ≥90 天）与过渡安排。否则一纸通知我们所有患者的服务立即中断 |
| C3 | 数据所有权与患者授权链路 | 明确患者授权给谁、我方以什么身份处理、授权撤回时双方各自的义务 |
| C4 | 接口可用性 SLA 与故障响应时限 | 我们的临床服务建立在这条链路上 |
| C5 | 费用结构 | 一次性/按患者/按调用？随规模增长的成本曲线要算清楚 |
| **C6** | **排他性条款要警惕** | 不要接受"不得接入其他品牌 CGM"这类限制。我们明确要做第二供应商以避免单点依赖 |
| C7 | 退出条款 | 合作终止时，历史数据怎么办？我们能否保留？患者数据迁移怎么处理？ |
| C8 | 版本与兼容承诺 | 见 B7，要落到合同 |

### D 组 · 合规（不谈清楚会变成我方的法律责任）

| # | 问什么 | 依据 |
|---|---|---|
| D1 | **数据是否全程境内存储？** 有无境外服务器或境外模型调用？ | PIPL 第 38 条。进口品牌尤其要问 |
| D2 | 厂商与我方各自是"个人信息处理者"还是"受托人"？ | PIPL 第 21/23 条，决定责任划分 |
| D3 | 能否提供数据接收/委托处理协议模板？ | 我方需保存处理记录 ≥3 年 |
| D4 | 患者授权是在厂商 App 内完成还是我方完成？授权文本能否满足"单独同意"？ | PIPL 第 29 条，敏感个人信息必须单独同意，不能捆绑 |
| D5 | 注册证号、有效期、预期用途？ | CGM 是第三类医疗器械，注册证要在有效期内且预期用途与使用场景一致 |

### E 组 · 硬件与渠道

| # | 问什么 | 备注 |
|---|---|---|
| E1 | 出厂价/经销价、起订量、账期 | 公开零售价 60–150 元/枚（大促后），出厂价未公开，需询价 |
| E2 | 能否由厂商/持证经销商直销给患者，门店只做引流？ | **我方与门店都不持三类器械经营许可，不碰货不收款**。这是合规红线，不是偏好 |
| E3 | 有没有"服务包内含 CGM"的合作模式？ | 比单卖硬件更适合我们的商业形态 |
| E4 | 供货稳定性、缺货时的替代方案 | 服务包有履约承诺，断供会直接违约 |
| E5 | 佩戴指导、上门服务由谁承担？ | 老年患者不会自己贴 |

## 3. 谈判顺序建议

1. **先 A 组**。A1（原始读数）和 A5（时间戳语义）如果答案不对，后面都不用谈。
2. **再 B 组**，确定形态后我方才能估开发量。
3. **A、B 谈定后再谈 C 组商务条款**——因为条款要把 A、B 的答案写进去。
4. D、E 组可并行，由合规与采购分别对接。
5. **要求对方技术接口人书面回答 A、B 两组**。口头承诺在集成阶段不作数。

## 5. 已知陷阱（本项目实证）

| 陷阱 | 表现 | 怎么破 |
|---|---|---|
| **"支持数据对接"的歧义** | 对方指的是"医生能在我们后台看报告" | 追问："是我们的系统自动取数，还是人工登录看？给的是逐点数据还是报告？" |
| **"开放接口"的歧义** | 实际是项目制定制开发，不是自助 API，且要排期 | 追问："有公开文档和沙箱吗？还是需要贵司投入人力为我们定制？" |
| **能力与代价不分** | "允许多个连接"是真的，但没说续航代价 | 每问一个能力，追问一句"**有什么代价**"。要数字不要形容词 |
| **形态错配** | "给 SDK"听起来解决问题，但移动端 SDK 装不进嵌入式网关 | 明确说出我们的使用场景（"要装进一个常插电的小盒子里"），让对方判断可行性 |
| **口头承诺不落纸** | 技术对接时人换了、口径变了 | A、B 两组要书面答复；关键项进合同（C1、C2） |
| **静默升级** | 固件/SDK 升级打断集成 | 谈兼容承诺与通知期（B7、C8） |

## 7. 当前最优先要问的三个问题（2026-09-04）

如果时间只够问三个，问这三个：

1. **【硅基】贵司是否书面允许第三方专用设备（我方常插电采集盒）承载贵司 SDK？** —— **这是授权条款问题不是技术问题**。此前所有方案都默认可以，但从未确认过。**若为否，二期采集盒方案整体作废**，夜间覆盖随之塌掉。它比下面两条更靠前
2. **【硅基】传感器本地缓存深度是多少？断连几天后重连能补回来吗？** —— 决定一期患者多久必须同步一次，是一期数据完整性的关键参数
3. **【硅基】多连接并存把 14 天续航缩短到几天？要具体数字** —— 10 天以下会击穿数据充分性门槛，14 天以下会让体验包成本翻倍

次一级但同批可问：
4. **【硅基】456–521 这类成本口径无关，但请确认是否有 iOS SDK** —— 低风险 iOS 单路患者的数据通道目前无结论
5. **【三诺】给不给原始逐点读数？接入形态是云到云还是 SDK？** —— 决定第二供应商是否可用

> ⚠ 第 1 条的性质提醒：厂商销售通常不会主动说"我们的 SDK 只授权给患者自用手机"。这类限制往往写在开发者协议或授权书里。**要的是书面条款，不是口头"应该可以"**。
