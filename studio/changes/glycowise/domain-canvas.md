## 0. 切分依据（不只按技术相似度）

| 判据 | 在本画布中的应用 |
|---|---|
| **语言测试** | 临床说 TIR/TBR/AGP/低血糖事件；运营说达标率/续约率/人均管理数；患者说"血糖稳不稳、能不能停药"；数据侧说通道/去重键/佩戴率；合规侧说单独同意/处理者角色/执业范围。→ 五组词汇 = 至少五组不同的领域，不合并。 |
| **变更频率** | 临床规则随指南更新（**年度级**）；~~数据通道随厂商谈判变（**项目级，6 周提前量**）~~ → **修订（2026-09-04）**：硅基通道已商务确认，通道维度降为**季度级**（第二供应商三诺的谈判仍按项目级预留提前量）；**载体（carrier）是本次新增的独立变更维度**——载体部署形态（采集盒 / 患者手机 / 无）随人群与商务政策调整（**项目级**），载体固件与 App 版本随迭代发布（**月级**，且因设备在患者家里，必须考虑灰度与回滚）。**通道与载体是两件事，节奏不同、责任人不同，不得合并成一个维度**：通道变的是"数据能不能算"，载体变的是"人能不能救"；传感器型号参数随选型变（**项目级**）；服务包与话术随运营调（**月级**）；告警去抖/值班随排班调（**周级**）；资质与备案有**到期日**（事件驱动）。节奏不同 → 不捆在一起。 |
| **合规责任归属** | 「数据授权与同意」「系统出口闸门」「人工话术与物料合规」「方案签发与留痕」「审计留痕」「主体资质与执业范围」是**六个独立责任主体**，不能揉进业务领域——否则业务迭代会顺手改掉合规逻辑。 |
| **单写者原则** | 一个字段只能有一个域写（`quality_flag` 只有 D1 写、`wear_ratio` 只有 D3 算）。同一个量被多个域各算一遍，漂移方向永远是**乐观**的。 |
| **Core vs Supporting vs Generic** | Core = 别人抄不走 **或** 出事就致命；Supporting = 必要但不差异化；Generic = 标准能力，用现成的。 |
| **边界测试** | "整块拿掉后其余领域还讲得通吗？" 拿掉「器械交易」其余全部成立 → 可外置；拿掉「合规闸门」业务仍跑但**违法** → 独立责任而非可选装饰。 |

### 关于 Core 偏多的说明

本画布 Core 有 12 个，比常规多。原因是控糖场景的 Core 有**两种来源**，投入策略不同：

| Core 子类 | 含义 | 域 | 建设策略 |
|---|---|---|---|
| **Core-差异化** | 别人抄不走，是产品的竞争壁垒 | D1 D2 D3 D8a | 重投入，追求质量与可扩展性 |
| **Core-风险承载** | 抄得走，但出事就致命/违法 | D4 D5 D6a D6b D7 D11b D13 D18 | 追求**正确性与可举证性**，不追求功能丰富；宁可简单也要不可绕过 |

把两类混为一谈会导致资源错配——风险承载域被当成"功能"去堆，或被当成"辅助"去省。

## 2. 分类表与理由

| # | 领域 | 类型 | 理由 | 变更节奏 |
|---|---|---|---|---|
| D1 | 血糖数据摄入与归一 | **Core-差异化** | 中国没有一家 CGM 厂商给**自助** API（此判断仍成立），~~由此推出"无可用通道"~~ → **修订（2026-09-04）：硅基已谈成**，证明的正是"通道是谈出来的"这条判据本身——适配器框架 + 统一 schema 是抄不走的资产；同时时区/单位/会话一错全部下游结论全错（mg/dL 当 mmol/L 差 18 倍） | 项目级（每家厂商） |
| D2 | 临床规则引擎 | **Core-差异化** | 32 条规则的阈值、优先级、人群切换是临床可信度本身。别人抄得走公式，抄不走"哪条抢占哪条、什么情况降级、缺参数往哪边倒" | 年度级（随指南） |
| D3 | 血糖指标计算 | **Core-差异化** | 初稿判 Supporting，**三方评审一致推翻**。公式公开，但"哪些读数算有效"是临床判断：warmup、伪差、未复核 OCR、跨会话、跨品牌、时区不确定——任一口径错会**静默**产出错误的达标结论，并直接进医师签发 | 年度级（口径） |

## 3. 关系映射

符号：`──▶` feeds into ｜ `◀──▶` shares ｜ `══▶` orchestrates ｜ `─╫─` gated by（必经闸门）｜ `⇏` 禁止的连线

### 3.1 主数据流 —— 双通道（这是全画布最关键的结构）

```
  ┌─ S11 载体层（跑在患者家里／身上，不在我方机房：glycowise-carrier）┐
  │  ①【二期】采集盒 gateway_box（我方资产，常插电，7×24 覆盖夜间）  │
  │  ②【一期即可】患者手机 patient_phone —— 一期只要求**周期性同步** │
  │  【二期】多 BLE 连接并存 → ①② 同时在线互为冗余，解掉"外出即断档"  │
  │  传感器本地缓存 → 同步一次即整段回填：**完整性靠缓存，不靠常驻**  │
  └───────────────────────┬───────────────────────────────────────────┘
                          ║ sdk_ble_direct（原始读数 5–15 min 点）
                          ▼
                        ┌── 实时事件通道（不受 R01 约束，佩戴第 1 天生效）──┐
S11 载体 ══▶ D1 摄入 ───┤                                                   │
X1 硅基云 ──▶（云云路径）│   D1(reading + trend.computed) ──▶ D2 实时规则     │

    触发危急告警        │                        （预审冻结模板，不过运行时闸）│
```

> **修订说明（2026-09-04，两轮）**：~~原主数据流的左侧入口是「X1 厂商云 / 指血 BLE / 截图 OCR」三选一，其中 OCR 为 Phase 0 主线~~ → **修订一**：硅基已商务确认并提供移动端 SDK，主线改为 S11 载体 ══ `sdk_ble_direct` ══▶ D1。→ **修订二（用户拍板）**：**实时告警链路整体移二期**。
> ⚠ **注意图上标注的"【二期】"限定的是"7×24 常驻 + 实时告警"，不是 `sdk_ble_direct` 这条通道本身。** 一期同样可以走 SDK——患者手机装我方 App，**周期性同步**把传感器缓存回填上来；一期也可以走云到云。**两条路径在一期都成立，选哪条是实现问题。** 唯一的分期边界是：**一期没有实时告警**。
> 指血 / OCR / 手工始终为兜底，且**不得独立触发危急告警**（沿用流程二 D7a）。
> 载体层之所以画出来而不是等二期再画：它是本画布唯一一段**不在我方机房、可能整夜断开**的链路。D1 之后的全部结构（双通道、回流线、三闸门）都默认"读数会到"。**在一期，这个默认在夜间是不成立的**——而它不成立时不会报错，见 §6 的「静默失效」。

### 3.2 必须存在的回流线（初稿整条缺失，是坏数据抵达临床结论的最短路径）

```
D1 reading.corrected / superseded / retracted / review_approved
   ──▶ D3 metrics.invalidated{window}
       ──▶ D2 重判 ──▶ D4 撤销/补发告警
                   ──▶ D5 plan.evidence_stale ──▶ D12 队列 ──▶ 签发人复核
```
> 场景：OCR 把 13.2 读成 3.2 → D3 算出 TBR 8% → D2 触发 → D5 草稿 → 医师签发（快照冻结）→ 三小时后健管师复核发现读错。**没有回流线，就没有任何人会知道。**「依据快照不可变」必须配「快照失效通知」，否则不可变 = 错误的永久固化。

### 3.3 D1 ↔ D8a：唯一的紧耦合对，用两条单向事件解开

```
D1 ──▶ device.serial_observed{serial, first_seen} ──▶ D8a
D8a ──▶ session.opened / warmup_window / calibration.mismatch ──▶ D1（落标记）
```
> D1 不判断会话，D8a 不写读数。`dedup_key` 不含 session_id；session 归属是按时间点解析的**可重算属性**——否则迟到读数（OCR 补数 3 天后传、API 一次回填 14 天）会重复入库或错归到新传感器。

### 3.4 治理流（横切）

```
D7 授权 ══▶ D1（无同意不摄入）、D16（无同意不触达）、D3（撤回则指标不可用）、

D14 编排 ══▶ D5 草稿、D9 餐食抽取、D10 描述性总结     ⚠ 不编排 D4
```

### 3.5 受管制输出的四条外部路径（初稿全部缺闸门或缺线）

```
① 平台 ──▶ X5 飞书（每日汇总行）─╫─ D7(⑥第三方 SaaS 传输同意) ─╫─ D6a(脱敏)
   ← 这不是内部同步，是持续的对外提供行为（PIPL 23）

```

### 3.6 禁止的连线（架构护栏）

| 护栏 | 理由 |
|---|---|
| `D2 ⇏ D16` | 规则结论不得直连投递，必须经 D5 签发或 D6a 闸门 |
| `D14 ⇏ D4` | LLM 不得参与紧急告警的判定与分发 |
| `D6a ⇏ 紧急告警的运行时阻断` | 词库误命中会吃掉可能致死的告警（低血糖处置话术天然含"胰岛素/磺脲/停"字样），且 `gate.blocked` 只写审计，夜里没人看 |
| `D4 ⇏ is_backfill 读数` | 否则回填 14 天历史会把三周前的低血糖当实时危急值推进企微群 |
| `D4 ⇏ 患者侧告警（confidence<0.95）` | 未复核 OCR 单位误读会制造大量假低血糖，误报多了健管师和患者一起关告警 |
| `D2 tier ⇏ 任何商品` | R32 硬阻断"分层 → 产品组合" |
| `X4 产品 ⇏ 血糖指标的因果表述` | D6a 反方向硬阻断；D10 配对排除 SKU 事件 |
| `D11b ⇏ 减药` | 不得进承诺条款、KPI 公式、结营举证——商业激励不得压在用药决定上 |
| `D8a ⇏ 写 quality_flag` / `D3 ⇏ 重推导 quality_flag` | 单写者原则，只有 D1 写 |
| `D1/D2/D8a ⇏ 各自算 wear_ratio` | 唯一计算者是 D3；四份实现的漂移方向永远是乐观的 |
| `D2 ⇏ 缺参数时回落一般成人阈值` | 缺失时按最保守（老年/高危）执行并置 stale 标记 |
| `D9 社群应答 ⇏ 直接回复` | P0–P1 只入不出；未来若回复须 `─╫─ D6a` |

## 5. 必答的边界问题

### Q1 器械交易（CGM 买卖）在不在平台边界内？

**不在。** 依据：CGM 属第三类医疗器械，门店"代销"无豁免路径；平台上架须自取三类经营许可 + 网络销售备案 + 公示证照（风险 1 高、风险 2 中）。

**切割带来的四条接口**（无资金流、无库存）：
1. **引流线索 out** ─╫─ D7(⑦线索共享同意) ─╫─ D18(受让方证照有效)
2. **设备激活回执 in**：序列号 + 患者 + 激活时间 → D8a 开会话。这是平台唯一必须从交易侧拿到的东西。
3. **到期/续购提醒 out**：D8a `sensor.expired` → 门店 → 经销商
4. **不良事件回传**：`device.adverse_event_reported` → 持证方。三类器械使用单位有上报义务；传感器失效导致漏报低血糖是器械不良事件，不只是商业补偿问题。（此条不在 22 条清单内，是清单的遗漏）

**连带影响**：
- 服务包合同**不含器械，含租赁也不行**——出租三类器械同样是经营行为、同样需许可。（风险 15 的整改原文写"服务包只含服务与器械租用"，本画布采纳更严口径，显式否掉租赁）
- 小程序商城不出现器械 SKU → 由 **D11a 的 SKU 上架前置审核**执行（类目白名单，器械类一律拒绝），不是一句文档结论。
- 成本模型里 CGM 是外购成本不是自营收入。

**未决**：**"不卖"不等于"无义务"**。若引流入口是小程序内跳转，可能被认定为提供"医疗器械网络交易服务"，触发第三方平台备案义务。P0–P1 采用线下扫码/人工传递，最终形态需执业律师定性。见 §8。

### Q2 「分型分级」归哪个领域？

**拆成四段，四个领域各持一段，任何一个都不能独自把它推给患者。**

| 段 | 归属 | 内容 |
|---|---|---|
| 计算 | **D2**（R18） | FG_cgm + PP2h_cgm + GMI/TIR 辅助算 L0–L4；须先过 R01；**老年（R28）与妊娠（R31）禁用此表**——这是 G 级门槛规则，不是阈值切换 |
| 老年/妊娠替代 | **D2**（服务需求分层） | 独立口径：TIR/TBR/低血糖事件频次/依从性/独居，**不用 FG/PP2h 诊断式切点**。养老场景下多数患者 ≥65 岁，没有这条就会有人为了"能跑"把老年偷偷套进 8.0/10.0/16.7 表——那是把无指南背书的经验切点用在最不该用的人群上 |
| 存储 | **D15** | 服务分层标签只读挂载；字段名不得叫 diagnosis；**必须与 `disclosure_approved` 同表且默认 false** |
| 披露 | **D5 + D6a** | 医师确认后才可对外，措辞固定为"CGM 提示您的血糖处于 X 区间，建议由医生结合静脉血/糖化确认"；D6a 拦截未授权直推 |
| 使用 | **D11a** | 可用于服务档位推荐，但须 D7 营销同意 + opt_out；R32 硬阻断"分层 → 商品组合" |

理由：它同时是临床判断（CGM 不能诊断，8.0/10.0/16.7 无指南背书）、服务分层（决定推 A/B/C）和受管制输出（风险 11）。放进任何单一领域都会让另外两个属性失守。

### Q3 智能体是一个领域还是分散在各领域？

**分散。智能体是执行形态，不是领域。**

| 智能体 | 归属领域 | 说明 |
|---|---|---|
| 健康分析 | D3 + D2 的表达层 | 只接收结构化 summary，不接收 288 点原始序列 |
| 行为分析 | D9 + D10 | 事件抽取与响应统计的表达层 |
| 方案规划 / 方案生成 | D5 | 只产出 draft；状态机与签发权在 D5 |
| 审核服务 | **D6a** | 是闸门的实现之一，但闸门规则本身是确定性的，不由 LLM 定 |
| 社群应答 | D9 | **P0–P1 只入不出（纯抽取，不回复）**。名字暗示会回话，但回话的出口不在 D4 也不在 D5，极易直连群机器人绕过闸门——必须显式表态 |
| 服务自动分发 | D11a + D12 | 履约触点调度 |

**唯一独立成域的是 D14**（Supporting）：编排、提示词版本、工具契约、模型日志、**生成式 AI 备案主责**、**模型部署地与数据驻留**（纳入 D7 出境拦截）。

**硬约束**：D4 紧急链路不经任何智能体。危急值判定必须确定性、可复现、可举证；LLM 的不确定性在这条链路上是纯负债。

### 自建插件（Core，投入质量）

**Core-差异化 —— 追求质量与可扩展性**

| 领域 | 关键工程点 |
|---|---|
| D1 摄入与归一 | **适配器 SPI 的契约是 `fetch → map`，不是 `fetch → normalize`**。适配器只输出未归一候选记录（`value_raw / unit_raw / device_time / vendor_tz_hint / device_serial / vendor_record_id / channel`）；归一、去重、会话关联、质量打标全在 D1 公共管道，适配器一行都不碰——否则每家厂商各做一套时区推断，就有 N 种默认值。通道属性做成一张表而非枚举。适配器版本号入库，支持重算派生列 |
| D2 规则引擎 | 规则表数据化（阈值/级别/依据引用可配），不写死代码；**实时通道与汇总通道分开部署与测试**；优先级排序器独立可测；每条规则能回答"依据哪一版指南" |
| D3 指标计算 | Python 自研（pandas/polars）规避 GPL；iglu 离线对拍作回归基准；**有效读数纳入口径写成显式配置并单测覆盖**；`sufficiency_ok / tz_uncertain / brand_changed / metric_provenance` 是输出契约一等字段；**分母取自 device_model，不硬编码 288** |
| D8a 会话与血缘 | 状态机 + **device_model 参数数据化**；session 归属支持回填重算 |

#### `glycowise-carrier` 应该是一个新领域，还是归入 D1？——**归入 D1，但作为独立插件边界（二期）**

行为矩阵新增了 System actor **S11 载体采集**、实物资产实体 **`gateway_device`**、以及独立插件边界 **`glycowise-carrier`**。本画布据此判断如下：

| 判据 | 结论 |
|---|---|
| **语言测试** | 载体侧说的是"连上没有、心跳、缓存补传、续航、保活、固件版本"——这是**运维与设备语言**，不是新的业务语言；它的**目的**仍然是"把读数交给 D1"。→ 不构成独立领域 |
| **边界测试** | 整块拿掉 `glycowise-carrier`，其余领域全部讲得通（一期就是这么跑的：没有它，走云到云）。→ **可外置，不是必需领域** |
| **单写者原则** | 它不写任何 D1 之外的字段，只产出 `reading` 与 `carrier.heartbeat`。→ 是 D1 的**上游数据源**，与"厂商云 X1"同类 |
| **变更频率** | 但它的节奏与 D1 完全不同：D1 是平台代码（随时可发布、可回滚），载体固件跑在**患者家里**（灰度难、回滚难、故障要上门）。→ **必须独立发版、独立可测、独立可监控** |
| **部署位置** | **决定性的一条**：它跑在患者家里/身上，**不在我方机房**。它与平台之间是一段**可能整夜断开**的链路 |

**结论**：`glycowise-carrier` **归入 D1 的领域边界**（同一套语言、同一个下游、同一个单写者），但**必须是一个独立的插件与独立的发布单元**，不与平台侧 D1 同包。

理由用一句话说清：**领域边界按"说同一种话"划，插件边界按"一起崩溃、一起发布"划。** 载体和 D1 说同一种话，但它们不会一起崩溃——D1 崩了是我方运维事故，载体崩了是患者家里那个盒子的事故，后者要派人上门。把两者打成一个包，等于让平台的每次发版都去碰患者家里的设备。

**推论（写进架构约束）**：
- `glycowise-carrier` 与平台之间**只有事件契约**（`reading.uploaded` / `carrier.heartbeat` / `carrier.buffer_flushed{data_age}`），没有共享库、没有共享数据库；
- 它必须能在**离线状态下继续采集并缓存**，重连后补传并标 `data_age`——`data_age` 是 D1 判断"能不能触发实时告警"的唯一依据；
- 它的可用性是一个**独立的 SLO**，与平台 SLO 分开度量；
- **`gateway_device` 是实物资产不是软件对象**，其配发/绑定/回收/归还的责任主体在 D8a + D11a + D12，不在本插件（⚠ 法务未决：中继三类器械数据的网关是否构成"医疗器械附件"，若构成则须由持证方配发，见 §8）。

**Core-风险承载 —— 追求正确性与不可绕过，宁简勿繁**

| 领域 | 关键工程点 |

### 架构模式

**Core + Add-on，事件驱动，双通道 + 三闸门横切。**

- **双通道**是本架构最重要的结构：实时事件通道（D1 → D2实时 → D4）与汇总判定通道（D1 → D3 → D2汇总 → D5）。把实时告警挂在窗口指标域后面，等于结构性地保证低血糖告警是滞后的。
- **三道横切闸门**：入口 D7（无同意不进）、系统出口 D6a（不合规不出，落点在 D16 硬拒）、主体 D18（无资质不签）。三道都是**架构强制**，不是调用约定。第四道 D6b 覆盖人工渠道，**只能靠流程**。
- **可插拔点**：厂商适配器（D1）、传感器型号参数（D8a）、规则包（D2）、服务包配置（D11a）、禁用词库（D6a）。五处对应五种变更节奏，各自独立发版。

### ⚠ 夜间 Level 2 告警链路的「静默失效」（本轮设计最重要的一条发现）

这一条的优先级高于本节其余全部内容，因为它是**唯一一种从数据上看不出来的失败**。

没有 7×24 载体时，传感器**照常工作**：它整夜把读数缓存在片上，次日患者拿起手机（一期即患者打开 App 同步一次）时一次性回填。于是：

- 报告上的**夜间 TBR、AGP 夜间曲线、`hypo_episode` 计数全部准确**——D3 的指标层完全正确，R01 的 70% 门槛也照样通过；
- 而那一夜的低血糖，**当时没有任何人知道**。D4 收到的是 `is_backfill=true` 的历史数据，按设计（且按正确的设计）**不触发实时告警**。

**指标层完美、安全层为零，且这两种状态在数据上长得一模一样。** 一个夜间 TBR 3% 的患者，可能是"我们守了一夜、报了三次警、他补了糖"，也可能是"没有人在看，他自己扛过去了"——两份 AGP 一模一样。

连带后果比技术后果更严重：**值班表照排、健管师照守夜、一整夜不会响一次**。夜班岗位在制度上存在、在功能上为零。运营侧会得到"夜间告警量很低"这个看似良好的指标，并据此认为系统运行正常——**这是一个会自我确认的假象**。

**分期重划（2026-09-04 晚）之后，这条发现的地位变了，但没有变弱——它从"我们必须避免的失效"变成了"一期的既定事实"。** 一期不做实时告警（无论走云云还是 SDK 周期性同步），因此一期**结构性地没有当夜干预能力**。这不是缺陷，是被明确选择的范围边界；危险的只有一种情况：**把它当缺陷藏起来，或者当能力卖出去**。

⚠ **同时要挡住反方向的误读**：一期没有实时，**不等于**一期数据不全。传感器本地缓存 + 周期性同步 = 完整的 5 分钟粒度历史序列。下面这张"能说什么"的表之所以能成立，全部建立在"数据是完整的"这个事实上——**如果连数据都不全，一期连"次日纠因"都做不了**。

因此，两条约束的表述随之更新：

> **一期（现在）**：~~D-02 夜间值班责任人是上线阻塞项~~ → **修订：D-02 降级为二期前置条件，不再阻塞一期上线**。一期不承诺夜间响应，也就不需要夜间值班；反过来说，**一期任何情况下都不得含夜间安全承诺**——这不再是"暂时不能说"，而是"这一期就是没有这件事"。D6a 词库须把"夜间监护 / 夜里出事有人知道 / 24 小时看护"列为**一期全局硬拦截**（一期 `carrier_registry.coverage_window` 恒为"不保证"，无需逐患者开关；逐患者开关是二期的事）。
>
> **二期**：**D-01（载体到位）与 D-02（夜间值班责任人）是同一个问题的两半，只解其一都等于零。** 有载体没人值班 = 凌晨三点的告警发给一个关机的手机；有人值班没载体 = 值班的人整夜等一条永远不会来的消息。二期启动前必须两者同时落地，否则二期交付的是一个**看起来有、实际没有**的夜间安全网——比一期"明确没有"更危险。

**一期该怎么讲低血糖，才既真实又有价值：**

| 说法 | 一期能否说 | 为什么 |
|---|---|---|
| "夜里出事我们会知道 / 会有人管" | **禁止** | 一期没有当夜链路。这是本文件级别的硬红线 |
| "我们能看出您夜里低过，并让医师据此调药" | **可以，且这是一期的真实卖点** | 次日的 `hypo_episode` 是**减药审查的客观证据**，比患者自述可靠得多——至心现在的做法是靠患者早上口头汇报。**前提是数据完整**，而缓存回填保证了这一点 |
| "您的 14 天报告是完整可信的、可以据此判断缓解" | **可以** | R01 门槛在一期真正达标，GMI 替代路径成立（流程四 D7）。这与有无实时告警无关 |
| "睡前血糖偏低会提醒您加餐" | **可以** | R08 作用在次日复盘推送上，是教育性提醒不是急救 |
| "连着低两次会自动收紧阈值并叫医师复核" | **可以** | HAAF 状态机不依赖实时，只依赖读数到齐 |

**失去的是当夜的干预，保留的是次日的纠因。** 这两件事在临床上都有价值，但它们不是同一件事，话术上必须严格分开——把"次日纠因"讲成"实时守护"，就是用一个真实能力去兑现一个不存在的承诺。

### 由此派生的一条最高优先级显示规则

> **"没有数据"和"没有异常"，在老人端、子女端、健管师队列三处都不能长得一样。**

这条规则约束 D12（工作台队列）、D16（触达）与所有患者/家属可见界面，优先级高于本画布几乎所有功能项。**一期同样适用，且一期更需要**——一期数据到得晚，"今天还没有数据"是常态而不是异常：

| 端 | 「没有异常」 | 「没有数据」必须长成 |
|---|---|---|
| 老人端 | "今天平稳" | **不得出现任何平安措辞**；显示"还没收到您的数据，请打开一次 App 同步"+ 一键呼叫。<br>**SDK 路径下这句话是功能而不只是提示**——它是把同步这件事交回给患者的唯一触点 |
| 子女端 | 绿色状态 + 当日摘要 | **数据缺口状态独立呈现**，并明示一期"不提供夜间实时监护"——不要让她以为自己买到了这个 |
| 健管师队列 | 不入队 | **必须入队**，且与"有异常"是**两个不同的队列**，不得合并排序被淹没 |

**最危险的形态是：数据没到，账照付，卡片照发"今天平稳"。** 这不是显示 bug，是把"我们没看见"说成了"没事"。

### 分期与领域的对应

> **分期已于 2026-09-04 晚重划（用户拍板）**：~~一期做 SDK/BLE 直连 + 实时告警~~ → **实时告警链路整体移到二期**。
> 理由：项目的绝大部分复杂度都从实时告警这一条链路衍生——**采集盒硬件、7×24 常驻与后台保活、双路 BLE 与传感器续航冲突、夜间值班编制，四个问题全都挂在它下面**。砍掉这一条，一期范围立刻收敛，且不再依赖任何一件我方无法单方决定的事（硬件、门店增编）。
>
> ⚠ **分期的边界只有一条：一期没有实时告警。** 一期走哪条通道**不是分期条件，是实现选择**——有云侧接口就走 `vendor_api`（云到云），没有就走 `sdk_ble_direct`（患者手机装我方 App，**周期性同步**）。两条路径在一期都能交付**完全相同的回顾性能力**。
>
> ⚠ **数据完整性 ≠ 实时性——这是理解本次分期的关键，也是最容易搞错的一点。** 硅基传感器**在本地缓存读数**，患者手机只要周期性连上一次，就能把整段缓存回填。因此 5 分钟粒度的历史序列是**完整的**：**R01（14 天 + ≥70%）在一期完全可以满足**，TIR/TBR/CV/GMI/AGP 全部成立，GMI 可用于缓解判定。**一期损失的只有时延**，而时延正是二期要解决的。<br>把"没有实时告警"读成"数据不全"，会连带砍掉一期本来就能交付的全部临床价值——这个误读的代价比分期本身大。

## 8. 待用户确认（技能第 7 步 Validate 未进行）

**A. 会改变工程量与排期的**

1. **D3 上调 Core + 双通道拆分 + 回流链路**，三项加起来对 P1 的工程量是实质增加。可能需要从 D10 餐后响应挪出人力，或把 D10 整体推到 P2 后段。
2. **X2 HIS 化验值与用药读入提前到 P1**（原计划 P2 才碰 HIS）——R17/R29/R30/R08/R27 全依赖。至心/德心的 HIS 是否具备接口、走什么协议，需一手确认。若做不到，只能靠健管师手工录 HbA1c 与用药类别，D12 要加录入项，且 D2 会长期处于"最保守阈值 + stale 标记"状态。
3. **P0 新增三个域**（D6b 话术库、D13 审计、D18 资质台账）。这三个技术上都不重，但都是"不做就违法"的项，不能推到 P1。
4. **生成式 AI 备案在 P0 启动**（原排 P2）。备案有周期，晚启动会卡住 P2 的智能体上线。

**B. 需要法务/外部拍板的**

5. **X3 引流入口的实现形态**：小程序内跳转经销商是否构成"医疗器械网络交易服务"、是否触发第三方平台备案义务。这决定小程序怎么做。P0–P1 先用线下扫码规避，但最终要律师定性。
6. **服务包"不含器械（含租赁）"** 的更严口径需与至心/德心商务确认——这与他们现有的打包方式可能冲突。
7. **处理者角色定性**（我方 vs 门店 vs 厂商：受托处理 or 共同处理者）。它决定同意书文本、PIPIA 范围、出事时的责任分担。

**C-bis. 前提变更（2026-09-04）后新产生的待确认**

9b. ~~⚠ **【一期唯一的前提风险】硅基的"云到云"是否可得？**~~ → **降级（2026-09-04 晚）：这是实现选择题，不是一期成立的前提。** 有云侧接口就走 `vendor_api`，没有就走 `sdk_ble_direct`（患者手机装我方最小 App，周期性同步），**一期照做**。仍需向硅基问定以便选路：① 云侧是否有开放接口/机构端授权；② 延迟；③ 拉取方式（增量游标 / 全量窗口 / 推送回调）与配额限流。<br>**连带降级**：~~"云侧读数是否带同一套传感器序号"~~ → 走 SDK 路径时**不存在这个问题**（行为矩阵 A1-6 已确认 SDK 侧读数默认带传感器序号，`dedup_key` 的序号预留 R-1 直接成立）；**仅在选择云云路径时才需问定**。

9b-新. ⚠ **【一期真正的关键参数，最高优先级】硅基传感器的本地缓存深度是多少？**（能缓存几小时 / 几天的读数）
   走 SDK 路径时，**患者多久同步一次决定数据完整性**。传感器缓存不是无限的：超过深度就**从最早的读数开始丢**，而且丢掉的部分**无法追回**。缓存深度直接决定：① **最长可容忍的同步间隔**；② 同步中断多久必须升级为电话工单；③ 服务包能不能对"数据完整率"作出承诺。
   **这是一期唯一会真正损害数据完整性的路径**，也是唯一一个"不问清楚就没法设计"的参数——它决定的不是体验好坏，而是 R01 门槛能不能守住。
   典型风险画像是老年患者（persona 01 刘阿姨）：她不会主动打开 App。若缓存只有 8 小时，她的数据会天天有缺口；若有 14 天，则"到店时自动同步"这一条就足够兜住整个服务周期。**同一个设计，在两个参数值下是两个产品。**

9c. **iPhone 用户是否也发采集盒**（二期）。iOS 后台 BLE 受限，**常驻**形态在 iOS 上大概率不可靠。**一期不受影响**——一期只要求周期性同步（用户主动打开 App 或前台唤醒即可），不依赖后台 BLE。二期必须决策，且它直接影响硬件预算与资产管理规模。

9d. **多路 BLE 并存对传感器续航的影响**（二期）。行为矩阵 A1-8 提示同一传感器多连接会显著缩短续航。**一期的周期性同步不是常驻连接，此风险在一期不触发**（这一点在澄清一期定义后更明确了）；二期必须真机实测，否则"盒子 + 手机双路冗余"这个卖点可能以"传感器提前没电"的形式反噬。

9e. **`gateway_device` 是否构成"医疗器械附件"**（二期，法务）。若构成，则与 X3「门店不碰货、不收款」的红线冲突，网关须改由持证方配发，整个资产流程的责任主体要换人。
