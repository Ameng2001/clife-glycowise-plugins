## 零、读这四份流程之前必须先知道的一件事

### 夜间 Level 2 告警链路的「静默失效」

这是本轮设计最重要的一条发现，放在最前面，是因为它会改变你读后面每一份流程的方式。

**没有 7×24 采集载体时，传感器照常工作。** 它整夜把读数缓存在片上，次日患者拿起手机（一期即打开硅基自家 App）时一次性回填。于是：

- 报告上的**夜间 TBR、AGP 夜间曲线、`hypo_episode` 计数全部准确**——流程三的指标层完全正确，R01 的 70% 门槛照样通过；
- 而那一夜的低血糖，**当时没有任何人知道**。流程二收到的是 `is_backfill=true` 的历史数据，按设计（且按正确的设计）**不触发实时告警**。

**指标层完美、安全层为零，且这两种状态在数据上长得一模一样。** 一个夜间 TBR 3% 的患者，可能是"我们守了一夜、报了三次警、他补了糖"，也可能是"没有人在看，他自己扛过去了"——两份 AGP 一模一样，两份报告一字不差。

**连带后果比技术后果更严重**：值班表照排、健管师照守夜、**一整夜不会响一次**。夜班岗位在制度上存在、在功能上为零。运营侧会看到"夜间告警量很低"这个看似良好的指标，并据此认为系统运行正常——**这是一个会自我确认的假象**。

### 因此，一期与二期的安全边界必须写死

**分期已于 2026-09-04 晚重划（用户拍板）：实时告警链路整体移到二期。**
理由是复杂度归因——采集盒硬件、7×24 常驻与后台保活、双路 BLE 与传感器续航冲突、夜间值班编制，**四个问题全都挂在实时告警这一条链路下面**。砍掉它，一期范围立刻收敛。

> ⚠ **分期的边界只有一条：一期没有实时告警。** 一期走**云到云**还是走 **SDK**（患者手机装我方 App、周期性同步）**不是分期条件，是实现选择**——有云侧接口就走云云，没有就走 SDK。两条路径在一期交付的能力**完全相同**。

> ⚠⚠ **数据完整性 ≠ 实时性。这是读这四份流程最容易犯的一个错，也是代价最大的一个。**
> 硅基传感器**在本地缓存读数**。患者手机只要**周期性连上一次**，就能把整段缓存回填上来——不需要 7×24 常驻，不需要后台保活。因此 **5 分钟粒度的历史序列在一期是完整的**：R01（14 天 + ≥70%）**完全可以满足**，TIR/TAR/TBR/CV/GMI/AGP 全部成立，GMI 可用于缓解判定（流程四 D7），餐后响应配对成立（流程二/三）。
> **一期损失的只有时延。** 而时延正是二期要解决的东西。
> 把"没有实时告警"读成"数据不全"，会连带砍掉一期本来就能交付的**全部**临床价值——这个误读的代价比分期本身还大。

| | **一期（无实时告警）** | **二期（7×24 载体 + 实时）** |
|---|---|---|
| 数据到达 | **两条路径任选**：① 云到云（患者用硅基自家 App → 硅基云 → 我方拉取）；② SDK（患者手机装我方最小 App，**周期性同步**，传感器缓存整段回填） | 采集盒 / 我方 App **常驻** BLE 直连传感器 |
| 数据完整性 | **完整**（5 分钟粒度，R01 可达标） | 完整 |
| 时延 | **一个同步周期**（小时级到一天级） | 分钟级 |
| 当夜干预 | **结构性地没有** | 有（前提：D-01 + D-02 双落地） |
| 夜间值班 | **不需要**（因为不承诺） | **必须有**，否则整期归零 |
| 低血糖的价值形态 | **次日纠因**：`hypo_episode` 作为医师减药审查的客观证据 | **当夜救援**：2 连续读数 + 预测性告警 |
| 一期特有风险 | **同步间隔**：患者长期不同步 → 传感器缓存溢出 → **丢数且不可追回**（见流程二 §2.5c、流程一「同步节律」） | 载体离线、续航（A1-8） |

> **一期的安全边界（硬红线，不是临时状态）**：一期**没有当夜干预能力**。服务包与所有对外话术（含流程三的 AI 输出与流程一/二的人工话术）**不得含任何夜间安全承诺**。这不再是"通道上线前暂时不能说"，而是**这一期就是没有这件事**。D6a 词库把"夜间监护 / 夜里出事有人知道 / 24 小时看护"列为**一期全局硬拦截**。
>
> **同时，一期在低血糖上确实有真实且可交付的价值，不要因为不能说实时就把它说没了**：至心现在靠患者早上口头汇报来判断昨夜有没有低过；一期给出的是**客观的夜间 `hypo_episode` 证据**，直接驱动医师做减药审查。**失去的是当夜的干预，保留的是次日的纠因。** 这两件事都真实，但不是同一件事，话术上必须严格分开——把"次日纠因"讲成"实时守护"，就是用一个真实能力去兑现一个不存在的承诺。
>
> **二期的前提（两者缺一不可）**：**D-01 载体到位** + **D-02 夜间值班责任人**。有载体没人值班 = 凌晨三点的告警发给一个关机的手机；有人值班没载体 = 值班的人整夜等一条永远不会来的消息。**只解其一都等于零。**

### 由此派生的一条最高优先级显示规则

> **"没有数据"和"没有异常"，在老人端、子女端、健管师队列三处都不能长得一样。**

它约束流程二的推送、流程三的报告、流程一的离店告知与所有患者/家属可见界面，**优先级高于这四份流程里几乎所有功能项**。一期尤其需要它——一期数据到得晚，"今天还没有数据"是常态而不是异常：

| 端 | 「没有异常」 | 「没有数据」必须长成 |
|---|---|---|
| 老人端 | "今天平稳" | **不得出现任何平安措辞**；显示"还没收到您的数据，请打开一次 App 同步"+ 一键呼叫。<br>SDK 路径下这不只是提示，**它是把"同步"这件事交回给患者的唯一触点**——而同步不做，缓存就会溢出丢数 |
| 子女端 | 绿色状态 + 当日摘要 | **数据缺口状态独立呈现**，并明示一期不提供夜间实时监护——不要让她以为自己买到了这个 |
| 健管师队列 | 不入队 | **必须入队**，且与"有异常"是**两个不同的队列**，不得合并排序被淹没 |

**最危险的形态是：数据没到，账照付，卡片照发"今天平稳"。** 这不是显示 bug，是把"我们没看见"说成了"没事"。

### 主线 2：临床安全（低血糖优先）

**告警口径 ≠ 事件口径**（专家评审的头号纠正，**C-01**）：Danne 2017 的「**持续 ≥15 min**」是**事后计数 `hypo_event` 与 TBR 统计**的口径，**只用于统计，永不用于实时触发**；**实时告警取即时确认口径 = 连续 2 个读数确认即推送，并叠加预测性告警**（`G + slope×20min < 3.9`，或快速下降箭头），目标是在**跌破阈值之前**就报出。等 15 分钟再推，患者可能已进入 Level 3——把统计定义拿去做触发条件，等于人为把告警延后一刻钟。两个口径在实现上必须是两段代码、两张表、两套测试。

> **分期说明（2026-09-04 晚，用户拍板）**：**实时告警链路整体移到二期**，一期只做云到云对接。上面这条 C-01 修正**仍然是本项目的正式口径**，但它的落地位置在**二期**（流程二 §2.2 的实时分支）。
> **一期保留的是"事件口径"这一半**：`hypo_episode`（持续 ≥15 min）照常统计，次日推给医师做**减药审查**。也就是说，一期用的恰好是那个"不能拿来做告警"的定义——而这正是它被设计出来的用途。**一期把 15 分钟口径用对了地方；二期必须避免把它用错地方。**

**Level 1 静音必须按人群分层，不得全局静音**（**C-05**）：~~夜间一律静音 Level 1~~ → **无感知低血糖（IAH）高危人群反而要把低值阈值上调到 4.4 并保留告警**——指南对这类患者的处置方向与"降噪"是**相反的**。判据是「用药 ∩ {胰岛素, 磺脲} ≠ ∅」或有 IAH 线索（老年 + 长病程 + 反复无症状低值）。降噪的对象是**子女端的打扰**，不是**患者本人的提前量**。此项在一期表现为"次日复盘的分层措辞"，在二期表现为"告警是否发出"。

**质量标记只能降级指标，不能降级安全告警**：`out_of_range` / `noise` / 低置信度都不得抑制 P0 低血糖链路。但 OCR / 手工通道**不得独立触发危急告警**（流程二 D7a），须经指血复测或人工复核确认——两条规则方向相反，但各自守的是不同的错误。

AGP 读图顺序「先低血糖 → 再高血糖 → 再波动」在三处被强制体现：
1. **流程二规则引擎**：P0 低血糖分支短路抢占，硬编码、不经 LLM、不受限流丢弃。
2. **流程三报告解读**：D3（TBR，R09）在 D4（高血糖）与 D5（波动）之前，超标时报告首行标红并直送医师做去强化审查。
3. **流程三人工签发**：TBR 超标时营养师分支必须等医师完成去强化审查，不能先推饮食建议。

### 主线 3：数据充分性门槛（R01）

`active%` 的分子**只计连续监测读数**：`vendor_api`（**一期主通道，硅基云到云**）/ `sdk_ble_direct`（**二期**，SDK 直连传感器）/ `ble_cgm`。OCR、指血、手工录入一律不进分子。分母 = 窗口天数 × (1440 ÷ `expected_sampling_interval`)。

**双路并存时的去重口径（二期新增，一期不触发）**：二期采集盒与患者手机可**同时连同一枚传感器**（硅基确认允许多个 BLE 连接并存），同一条读数会**经两条路各到达一次**。三条规则：

1. **自然去重**：`dedup_key = patient + vendor + device_serial + reading_type + time_utc(取整到分钟)` 已经不含 carrier，两路同源读数天然落到同一个 key，**去重在 D1 完成，指标层看不到重复**。
2. ⚠ **但取整到分钟不是安全的**：两路设备的时钟存在微小偏差（盒子与手机各自对时，几秒到几十秒），**同一个 5 分钟采样点可能被两路上报为 `10:04:59` 与 `10:05:01`，取整后落在相邻两分钟，去重失效**，于是同一条读数被计入分子两次，`active%` 被虚高。<br>**处理规则**：去重键的时间分量改用**采样序号优先**（`vendor_record_id` / 传感器侧序号存在时以它为准，与 carrier 无关）；无序号时，对同一 `device_serial` 在 **±90 秒窗口**内的同值读数视为同一读数，保留 `is_primary=true` 那一路，另一路标 `duplicate_by_carrier` 入库但**不进分子、不进指标、不触发告警**。
3. **同一时刻两路都有数据，分子只算一次**——这条要写进单测。`active%` 度量的是"这一刻传感器的读数有没有到平台"，不是"到了几份"。载体冗余提高的是**到达概率**，不是**读数数量**；把冗余算成覆盖率，就是用备份把体检报告刷成满分。

~~**推论（必须写进入组话术与合同）**：纯降级通道下 R01 永远不通过，该患者的报告长期只能是 `trend_only`。这不是缺陷，是通道现实。~~
→ **修订（2026-09-04）：退为兜底场景说明，不再是主线现实。** 硅基通道已商务确认，一期即走云到云，**R01 的 70% 门槛可以真正达标**，指标层与缓解判定成立。上述推论现在只适用于三类**兜底场景**：① 硅基之外、尚未谈成通道的其他品牌患者；② 患者自带境外品牌（如雅培 LibreView，PIPL 38/40 禁止云到云）；③ 主通道故障期间的降级窗口。这三类患者仍然长期只能是 `trend_only`，入组话术仍须说明——但它们已经是**少数派而不是全体**。

`days≥14 AND active%≥70` 是所有结论的前置条件，在三处设卡：
- 流程二 D6：不足则只出趋势描述。
- 流程三 D1：不足则整份报告降级为 `trend_only`。
- 流程四 D1/D7：不足则不得用 GMI 替代 HbA1c 做缓解判定。

### 主线 3b：`channel_registry` + `carrier_registry` —— 两张必须先落地的表

~~原为一张 `channel_registry`~~ → **修订（2026-09-04）**：前提变更后必须拆成**两张表**，因为它们回答的是两个不同的问题，且**在一期它们的答案是相反的**（通道到位、载体缺位）。

| | `channel_registry`（通道） | `carrier_registry`（载体） |
|---|---|---|
| **回答什么** | **数据能不能算** | **人能不能救** |
| 决定 | R01 门槛、指标是否成立、GMI 能否替代 HbA1c、报告口径（正式 / `trend_only`） | 实时告警是否可能、夜间是否有覆盖、能否承诺"夜里有人看"、本机强制提醒是否可用 |
| 字段 | `vendor / model / capability_level（cloud_api\|report_only\|pilot\|none）/ storage_region / sampling_interval / warmup_minutes / max_window_days / rate_limit / is_incremental_cursor / supports_realtime_alert / MARD / observed_latency_p95 / 合同与 DPA 编号` | `patient / carrier_type（gateway_box\|patient_phone\|none）/ heartbeat_interval / last_seen / coverage_window / supports_local_forced_alert / bound_sensor_sn / firmware_version / is_primary` |
| 粒度 | **逐厂商 × 型号**（租户级主数据，BD/技术维护） | **逐患者**（甚至逐患者多条：盒子一条、手机一条） |
| 变更节奏 | 季度级（硅基已确认后） | 项目级（部署形态）+ 月级（固件） |
| 一期取值 | 硅基 `capability_level=cloud_api`（走云云）**或** `sdk_ble_direct`（走 SDK）——**二选一是实现决策，不影响一期能力** | `carrier_type ∈ {none(云云), patient_phone(周期性同步)}`、`coverage_window=不保证`、`supports_local_forced_alert=false`、**`last_sync_at` 是一期最需要盯的字段** |

**为什么必须是两张表而不是一张表加几个字段**：一期的现实是**通道满分、覆盖零分**——数据全都到得了，只是**晚一个同步周期**。合成一张表就会出现"通道可用 ⇒ 可以承诺告警"这种顺理成章的错误推导，而这条推导**在一期恰好是错的**。分成两张表，是让"我们看得见"和"我们来得及"在系统里必须被分别回答。

依赖 `channel_registry` 的判断点：流程一 D11/D11a/D11b、流程二 SLA 定义与 X13 限流、流程三 D1 的 `expected_sampling_interval`、流程四 D7 的 GMI 替代资格。
依赖 `carrier_registry` 的判断点：流程二告警是否发出与 SLA 承诺、流程一离店时的覆盖告知、D6a 对"夜间监护"类话术的拦截、子女端"今晚有没有兜底"的显示。
