> ## ⚠ 读本文之前：分期与安全边界（2026-09-04 修订）
>
> **分期的唯一边界是：一期没有实时告警。** 本文档的**实时告警分支全部属于二期**，文中以【二期】标注，**保留而不删除**——二期要用，且它的正确口径（C-01）现在就必须写对，否则二期实现时会重犯同一个错。
>
> **一期走哪条通道不是分期条件，是实现选择**：有云侧接口走 `vendor_api`（云到云），没有就走 `sdk_ble_direct`（患者手机装我方最小 App，**周期性同步**）。**两条路径在一期交付的能力完全相同。**
>
> ⚠⚠ **数据完整性 ≠ 实时性。** 硅基传感器**本地缓存读数**，手机周期性连一次即整段回填。因此**一期的 5 分钟粒度历史序列是完整的**：R01 可达标、TIR/TBR/CV/GMI/AGP 全部成立、餐后配对成立。**一期损失的只有时延。**
>
> **一期的安全边界（硬红线，不是临时状态）**：一期**没有当夜干预能力**，服务包与所有对外话术不得含任何夜间安全承诺。低血糖在一期的价值形态是 **"次日纠因 + 为医师提供减药证据"**——这是真实且可交付的，但必须与"实时救援"严格分开表述。
>
> **一期保留的三条不依赖实时数据的临床安全能力**（本文中已建模，均归一期）：① **低血糖证据通道**（次日 `hypo_episode` → 医师减药审查）；② **睡前低值预警 R08**（作用在次日复盘推送上）；③ **低血糖状态机 D12b**（HAAF：24h 内二次低血糖 → 阈值上调 + 医师复核任务）。
>
> **一期特有的新风险**：**同步中断 → 传感器缓存溢出 → 不可追回的丢数**。见 §2.5c。

## 一、流程元数据

| 项 | 内容 |
|---|---|
| **流程名称** | 居家 CGM 数据摄入 → 指标 → 规则引擎 → 分级告警 → 响应闭环 |
| **触发** | ① **硅基主通道**：`vendor_api` 定时拉取（云到云）**或** `sdk_ble_direct` 患者同步上传（SDK 路径，**一期为周期性、二期为常驻**）② 患者上传截图/AGP PDF（兜底）③ 指血仪 BLE 上报（兜底）④ 健管师工作台手工录入（兜底）⑤ 定时任务（06:00 日报批算、每日静默检查、**同步中断检查**） |
| **结束状态** | ① 读数入库并计入指标 ② 读数入库但标记为不可用（噪声/超范围/预热/低置信待复核）③ 告警已闭环（有响应回执）④ 告警升级至危急值人工兜底并闭环 ⑤ 数据静默—已联系患者 ⑥ 摄入失败—进死信队列待运维 |
| **频率** | CGM 读数 288 条/人/天（5 分钟粒度）；拉取每 5 分钟；告警按事件；日报每日 06:00；静默检查每日 09:00 |
| **边界** | 含：多通道摄入、归一化去重、质量判定、指标计算、规则引擎、告警分级与推送、响应回执、静默与传感器生命周期。<br>不含：14 天 AGP 报告与方案调整（流程三）、缓解判定（流程四） |
| **关键 SLA（按通道分别定义，不得合并承诺）** | ⚠ **一期对外不承诺任何"产生→推送"的实时时延**——一期没有实时告警链路，本行的分钟级承诺**全部属于【二期】**。一期只承诺"**数据完整性**"（14 天 ≥70% 有效读数）与"**次日可见**"（每日复盘推送时点），不承诺"多久报出来"。<br>【二期】① 厂商云通道：`产生→平台可见` 受厂商侧延迟支配（国产云到云待 BD 确认，海外 Dexcom 明确 3h），平台**仅承诺 `平台可见→推送 ≤2 分钟`**；② 指血 BLE：`患者同步→推送 ≤2 分钟`；③ 截图/PDF：`上传→推送 ≤5 分钟`，**无上传即无告警**；④ 手工录入：无实时告警承诺。<br>**对外话术只能承诺"平台可见→推送"这一段，禁止承诺"低血糖 2 分钟内告警"。** 通道实际端到端延迟由 `channel_registry.observed_latency_p95` 每周实测更新。<br>响应侧【二期】：危急告警 推送→健管师响应 ≤15 分钟（日间）/ ≤30 分钟（夜间兜底）；高级 ≤60 分钟。**夜间响应 SLA 的前提是 D-02 夜间值班责任人已落地**——没有值班表，这个数字只是纸面。<br>**一期的响应侧 SLA 是另一套口径**：`hypo_episode` 产生 → **次日健管师队列可见 ≤ 日报批算完成时点（06:00）**；`hypo_episode` → **医师减药审查任务生成 ≤ 当日**。这两条一期就能兑现，且可度量。 |

### 2.5b 载体离线检测与分级（**二期**）

```
[载体心跳，间隔 ≤5 分钟]
    │
    ▼
◇ D23b 心跳是否丢失（> 2 × heartbeat_interval）？
    ├─ 否 → ◇ D23c **心跳有、读数无**？（这是与"心跳无"完全不同的信号）

    │          │        → 电话指导挪位置；标 `carrier_out_of_range`
    │          └─ 否 → 正常
    └─ 是 → ◇ D23d **分级**：这个患者还有没有第二条路？
              ├─ **盒子掉线，但手机仍在收**（双路冗余生效）
              │    → 级别 = **中**。标 `coverage_degraded`：
              │       · 白天覆盖仍在，**夜间覆盖已失效**（手机夜里在充电/静音）
              │       · **必须告知患者与家属"今晚没有夜间兜底"**
              │         —— 豁免于触达封锁，与 `consent.revoked` 同级
              │       · 生成健管师跟进工单（次日），不外呼
              ├─ **两路全断**（或本就只有一路，且它断了）
              │    → 级别 = **高**。标 `coverage_none`：
              │       · **立即电话，不发消息**（F1 的成因就是他在用手机）
              │       · 生成加急工单；连续 2 晚未恢复 → 上门/置换
              │       · **同时冻结一切"平稳/正常"措辞**（见"没有数据 ≠ 没有异常"）
              └─ **患者处于 away_mode**（回老家、住子女家）
                   → 级别 = **中**，但处置不同：不催修，**明确告知覆盖已暂停**，
                     约定返回日期；`away_mode` 不豁免告知义务
    ▼

```

> **为什么心跳与读数必须是两个独立信号**：合并成一个"在线"布尔值，D23c 与 D23d 就再也分不开——而它们的处置完全相反（一个是挪位置，一个是查电源）。这是流程一「载体交付的五种失败模式」F1 与 F2 的技术前提。

> **告知义务不是可选项。** 载体离线时，患者失去的不是一个功能，是**他以为自己有的一张安全网**。不告知的后果不是"体验差"，是他会**继续按有安全网的方式生活**（典型：以为夜里有人看，于是不再叫子女陪住）。因此覆盖状态变更的告知**豁免于一切触达封锁与免打扰设置**。

### 2.5c 同步中断检测与分级（**一期，SDK 路径**）

一期没有心跳可查——患者手机不常驻，"没同步"是常态而不是异常。**一期查的是 `last_sync_at` 与 `sync_plan` 的偏离度**。

```
[每日 09:00 + 每次同步后更新 last_sync_at]
    │
    ▼
◇ D23e 距上次同步 > `sync_plan.预期间隔` × 1.5？
    ├─ 否 → 正常
    └─ 是 → ◇ D23f **距缓存深度还有多远？**（这是一期唯一真正紧急的维度）
              │  ※ 传感器缓存溢出 = **从最早的读数开始丢，且不可追回**
              │  ※ 缓存深度**待向硅基问定**；问定前按 24h 保守假设
              ├─ 剩余 > 50% → 级别 = **低**：App 推送提醒 + 次日队列
              ├─ 剩余 20–50% → 级别 = **中**：按 `sync_plan.协助人` 分支
              │      · 老年画像 → **打给子女/同住家属**，不是打给老人
              │      · 自理画像 → 电话 + 短信
              │      · 有到店排期 → 提示健管师"到店时务必触发一次同步"
              └─ 剩余 < 20% → 级别 = **高**：**电话 + 约到店同步**
                     · 已进入缓解判定复测窗口的患者（流程四）→ **加急**，
                       因为这 14 天丢一段就要整体推迟判定
    ▼
◇ D23g 已经丢数了吗？（同步回来后，缓存首条读数晚于上次同步末条 + 采样间隔）
    ├─ 是 → 【标 `data_lost_by_overflow{from, to}`，**永久留痕、不可回补**】
    │        → 计入 R01 分母（**不得移出**——丢了就是丢了，不能靠调分母掩盖）
    │        → 报告中**显式披露该缺口**，不得静默平滑
    └─ 否 → 正常
```

> **这是一期唯一会真正损害数据完整性的路径，也是一期唯一"丢了追不回来"的东西。** 通道故障可以补拉、OCR 可以重传、指血可以补录——只有缓存溢出是不可逆的。因此它的工单优先级应当高于同等级别的其他数据质量问题。

> ⚠ **不要把"没同步"做成对患者的催促轰炸。** 老年画像的主路径是**到店自动同步**（周期性到店本来就是这套服务的形态），其次是子女协助，**最后才是提醒她本人**——因为提醒她本人恰恰是最不可靠的一环（她不会主动打开 App，这不是依从性问题，是产品对她的要求不合理）。

### 2.9 数据更正与撤销的级联（可回溯性核心）

```
[`ingest_batch` 回滚 / OCR 复核否决 / 迟到读数补入 / session 重归属]
    │
    ▼
[发事件：reading.retracted / reading.corrected / session.recomputed]
    │
    ├─→ ① 已发出且尚未闭环的告警
    │      → [发"该告警因数据更正已撤销"更正卡片；
    │         `alert_response` 记 `retracted_reason`]
    │
    ├─→ ② 受影响窗口的 `cgm_summary`
    │      → [标 `stale` 并重算]
    │      → ◇ 重算结果与原结果的差异是否触及达标结论？
    │           ├─ 是 → [**生成健管师/医师待办，不得静默覆盖**]
    │           └─ 否 → [静默更新]
    │
    └─→ ③ 已推送给患者的报告
           → [生成"数据更正说明"版本；
              报告表保留全部历史版本（`report_version` 单调递增，不可原地改写）]
```

※ 只回滚脏数据、不更正已发出的结论，等于"数据修好了，错误结论仍留在患者手里"。
  这是可回溯性最大的缺口。

## 四、并行说明

```
[reading.ingested] ──┬──→ [实时规则引擎（流式，毫秒级）] ──→ [告警]
                     │              ── 可并行，互不阻塞 ──
                     └──→ [指标计算（滚动窗口 + 06:00 批算）] ──→ [cgm_summary]

[企微群推送] ──┐
               ├── 可并行 ──→ 合流于 [alert_response 回执]
[工作台红标] ──┘

[厂商云拉取] ──┐
[截图上传]   ──┼── 多通道可并行，合流于 [Normalizer → Dedup]
[指血 BLE]   ──┤   ※ 同时段重复时 API 优先，OCR 标 superseded
[手工录入]   ──┘
```

关键约束：
- **质量标记只能降级指标，不能降级安全告警**（D3/D4/D5 均不抑制 P0 链路）。
- **告警链路绝不等指标计算**。指标是解释性的，告警是安全性的，两者必须解耦，规则引擎直接吃流式读数。
- **低血糖分支与其他规则不是"并行"而是"抢占"**。AGP 读图顺序（先低 → 再高 → 再波动）在引擎里体现为短路：命中 P0 后不再评估 P1/P2，且当次输出中不得混入饮食/产品建议。
- 多通道并行摄入的唯一合流保证：同一读数不论走哪条通道，落库后 `time_utc`、数值、单位、sensor 归属必须一致，通道差异只体现在 `source_channel` / `source_confidence`。

## 七、关键观察

**瓶颈**
1. **健管师的告警响应是全流程最脆弱的一环**。日间尚可，夜间（22:00–07:00）本质是靠人值班顶着。健管师人均管理目标（~~60 人~~ → 修订 C-02：分阶段 32/40/48）与"夜间 30 分钟响应"存在直接冲突——必须靠"误报压制 + 分级 + 自动外呼 + 子女端"共同摊薄，否则健管师会被噪声耗死，进而对真告警脱敏。
2. **OCR 复核队列**。修订（2026-09-04）：OCR 已从主通道退为**兜底**，此瓶颈大幅缩小。仅在主通道中断期间才会堆积（按人均 32–48 人计，每人每天 1–3 张 = 数十条），此时应优先修复主通道而非扩充复核人力。~~Phase 0 必须接受、Phase 1 必须消灭~~ → 一期起即为异常态，不是常态债。
3. **R01 数据充分性门槛与商业期待的冲突**。佩戴率不足 70% 时不能出结论，但患者付了钱就想要报告。降级输出的措辞与产品预期管理是运营难点，必须写进入组话术。

**自动化候选（安全）**
- 去重、单位换算、时区补齐、session 管理、质量标记 —— 完全自动化。
- 指标计算（TIR/TAR/TBR/GMI/CV/AGP/餐后配对）—— 完全自动化。
- 低血糖阈值判定与**告警触发** —— 自动化；但**处置话术必须是固定科普模板，不是 LLM 生成**。
- 静默检测、传感器到期提醒、限流去抖、SLA 计时与升级 —— 完全自动化。

**必须由人（不可自动化）**
- OCR 结果复核、校准差异超阈值时的取舍、患者报告餐时的确认（误差常 ±15 分钟）。
- 一切用药相关判断与回答（医师）。
- 危急值的临床处置决策。
- 分型/分级结论（医师，且对患者措辞须为"提示区间"）。

**通道现实性（数据对接专家的核心提醒）**
- `channel_registry` 是必须先落地的一张表：`vendor / model / capability_level / storage_region / sampling_interval / warmup_minutes / max_window_days / rate_limit / is_incremental_cursor / supports_realtime_alert / MARD / observed_latency_p95 / 合同与 DPA 编号`。**四份流程中所有"厂商通道是否可用"的判断一律查此表，不得各处独立二元判定。**
- 告警时效不是平台单方承诺，是通道属性。对外话术只能承诺"平台可见→推送"这一段。
- 摄入层最容易被忽略的四类非理想数据流：**乱序、迟到、更正、撤销**。前两者靠 SessionLinker 按 `device_time` 归属解决，后两者靠 §2.9 级联解决。

**设计红线**
- 低血糖链路**独立部署、硬编码、不经 LLM、不受限流丢弃、不与产品推荐同句出现**。这是整个系统里唯一"错了会死人"的路径。
- 任何输出附固定尾注；涉及方案变更的内容一律走流程三的审核闸。
- **告警口径与事件口径必须分开实现**：告警取"连续 2 读数确认"的即时口径，`hypo_event` 计数与 TBR 统计取"持续 ≥15 min"的 Danne 口径。把统计定义拿去做告警触发条件，是本系统最容易致命的一个实现错误。
